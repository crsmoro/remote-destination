# Experimental private-bridge Google and Auth0 egress (not a release)

`compose.egress.yaml` is an opt-in overlay for the quarantined `compose.yaml`. It adds no Traefik route or host port. The backend remains on the internal `quarantine` network; only the egress relay joins both `quarantine` and its dedicated outbound bridge. The relay is also a peer of the backend and can reach its listener. Docker host, Docker administrators, relay image/process, network membership and DNS infrastructure are trusted. Do not add other containers to either bridge. This overlay is independent of the inbound mTLS design and does not implement it.

To inspect locally, without starting anything:

```sh
export DEVICE_KEY_HOST_FILE=/absolute/path/to/existing/device-key
# Requires Docker Compose v2; inspect the merged output before any use.
docker compose -f compose.yaml -f compose.egress.yaml config
```

For an authorized isolated staging exercise only, use the same two `-f` arguments with `up --build` and later `down` (do not use `-v` if preserving its named data volume). No deployment has been performed. Images use the same mutable tags as the existing Dockerfile: pin reviewed digests for a release. Restrict access to Docker and secrets. Neither this file nor the overlay grants authorization to deploy.

`WAZE_EGRESS_PROXY=egress:3128` enables the dedicated relay; unset retains existing direct-dial behavior and any other value fails closed. Standard proxy environment variables are ignored. The backend validates Google URLs and redirects, and sends the allowed hostname to the relay without resolving it. The JWKS client also uses this relay when configured. The relay accepts exact allowlisted Google hostnames and the Auth0 hostname fixed in the relay source on port 443 (review that hostname before publishing), resolves each hostname itself, rejects the entire answer if any address is non-public, and connects to a validated literal IP. TLS stays end-to-end: the backend verifies the original hostname and sends it as SNI. Legacy literal-IP CONNECT remains restricted to IPs currently returned for allowlisted hosts. DNS and relay failures produce the existing warning/fallback for Google; JWKS failures deny agent authorization. The private backend needs DNS only for the relay service name; the relay needs external DNS. A CONNECT tunnel is not restricted to the JWKS path.

**Security limitations:** IP membership is not application identity. A compromised backend or another bridge member can tunnel arbitrary TLS or other bytes to a currently resolved Google IP, potentially reaching unrelated virtual hosts/services sharing that IP; this is not a complete hostname or HTTP-path firewall. It cannot tunnel to an arbitrary IP unless DNS for an allowlisted name resolves to it; a malicious or manipulated DNS server can therefore authorize arbitrary public IPs. Private/special ranges are denied but the list is not a substitute for independent egress firewall policy. The relay has unrestricted OS-level outbound access if compromised. It listens on both attached interfaces and has no client authentication; isolation depends on exclusive bridge membership and host firewall. It is experimental, not independently reviewed or resource-exhaustion hardened. Do not use as a security boundary against a compromised relay/host or hostile network members. For strict Google-only egress, require a separately reviewed enforcement mechanism that verifies destination identity and limits the relay's own outbound network access.

**Release gates:** test the real Compose topology and DNS, successful live Google short-link redirects with verified TLS, rejection of redirects to private/non-Google hosts, rebinding/mixed DNS, invalid certificates and mismatched SNI, unauthorized external/peer access, DNS failure, and cleanup. Review network/firewall and abuse limits. Existing inbound mTLS, authentication and deployment gates remain unchanged. The Go tests use isolated local fixtures; they do not prove the real Compose, Google network, firewall, or deployment behavior.
